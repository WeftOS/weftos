## 2. Target buckets

Names come from ADR-126 §2 and are derived, never chosen: `p-<ulid>`, `w-<ulid>-<h12(slug)>`,
`r-<ulid>-<h12(channel)>`, `n-<node id>`; the readable slug, owner and creation time are bucket tags.
Project ULIDs come from `weaver project add` on the host that owns the project (PG for every project
below), so the list here is by project, not by ULID.

**Two stores, two jobs** (ADR-130 §1 tiers): PG's RustFS is **L1**, the LAN staging and sharing
tier (unmerged worktrees other nodes should see before integration, dependency trees, gitignored
assets, release artifacts). GCS is **L2**, the durable integrated tier (seed heads, packs; ADR-131
adds one seed bucket plus one inbox bucket per client, §5.2). A client project therefore gets an L1
instance of its own on PG (S5, as the client user under `/data1`) and, when the owner answers
ADR-131 questions 2 and 3, a GCS bucket pair. Nothing of a client's goes into the `weftos`
account's RustFS.

## 5. The access path: materialise and watch, never a mount

**Prototype (2026-11-08):** the materialise-and-watch loop exists as a library on `wt/adr126-s3-drive`; see §7 row 9a and `docs/research/adr126-s3-materialise-watch-2026-11-08.md` on that branch.

Three layers, one rule: files a program reads are real files on the local file system, kept in step
by a daemon; nothing on the read or write path waits on the network; a notification is only a
wake-up, a poll is the source of truth.

1. **The seed drive (L2, ADR-131 §1 to §3).** Materialise by APFS clone, reflink or overlayfs;
   capture with FSEvents, inotify or fanotify plus an index scan; seal after 2 s quiet; device-signed
   layers to the inbox; verified refresh by clone. This is the weftos-d1 lane: a D1 daemon spike is
   on branch `feat/adr131-d1` at 8439f55f6 (clone-place, FSEvents, WAL ring, seal, refresh, kill
   points, offline kill test), timings pending gcloud and a quiet window. Not touched from here.
2. **Worktree buckets on RustFS (L1, ADR-126 §4 and §4a).** Already materialise-and-watch by
   construction: `worktree-store.sh fetch <slug> <dest>` materialises `.wt/tree` and the git bundle
   into a local directory with every object's SHA-256 checked and no silent overwrite;
   `follow`/`poll` watches the registry (one list plus one get per worktree, 30 to 60 s; a mesh
   notification only shortens the wait). The missing pieces are measurements (gate item 3, this
   lane) and a watcher that re-fetches changed paths into an existing materialised tree (today
   `fetch` is whole-tree; `sync-docs` is the only incremental mirror, docs only). That incremental
   refresh is the same code the drive needs (§5.1), so it should come from the drive crate, not be
   written twice.
3. **Gitignored assets (ADR-126 §4 overlay).** Reads fall through worktree to project through the
   daemon (`weaver store get`, `svc.store` for cogs). For a tree that wants them as files, the same
   materialise step places them; there is no mount. The S2 `rclone union` mount verb is parked
   (§1).

What "watch" is on each side today: on GCS, Pub/Sub on `head/` and `incoming/` (**proven**, SC
side) with the PG relay **not built**; on RustFS, bucket notifications are designed (ADR-126 §6)
with field names **unverified**, so S2 polls.
