## Photo-gallery storage and UID convention

The user designated `/data1/weavelogic-internal` for WeaveLogic-owned internal projects and `/data1/weavelogic-clients` for client projects. The WeftOS project's stable source/runtime root should be `/data1/weavelogic-internal/weftos`; the currently staged `/srv/weftos/projects/weftos` copy is a transitional location, not the intended final root. A client account's Linux home directory is the client directory itself, for example `/data1/weavelogic-clients/<client>/`, rather than `/home/<client>`. Project data beneath that home stays owned by its project-specific UID, with no cross-project sharing by directory permissions or a common rootless Podman store. If one client has multiple projects, assign a distinct UID and home to each project under the client's subtree; do not assume the client slug and the project UID are interchangeable. The existing `weftos` internal account is UID/GID 2101 and currently has `/home/weftos`; moving its project root does not silently change that account home. The `weavelogic` operator account remains UID/GID 2100. Only the internal WeftOS pilot may temporarily share its UID with its machine service; the exception does not extend to any client.

The user also directed an internal archive landing zone at `/data1/weavelogic-internal/_archive/`. Stage a non-destructive, resumable copy of the operator Mac's `~/dev/` into `_archive/dev/` and `~/aepod-xpc-sync/` into `_archive/aepod-xpc-sync/`, preserving each source namespace and recording copy and verification receipts. The latter was checked locally as 44 GB and contains `.tgz` project archives, including a `clients/` subtree; some projects may already have been restarted elsewhere. Do not equate an archive copy with an enrolled project. Promote each selected internal project into its own governed project root later, after identity, UID, provenance and predecessor decisions; similarly copy client projects into their intended client homes only after matching the project and owner. Keep originals until the archive has been verified and the user decides retention.

## Existing contracts and gap

The dashboard has `workspaces`, `projects` and `nodes`. A project has a workspace UUID, slug and kind; a node may be linked to a project (`supabase/migrations/202609260001_control_board.sql:3-19,68-77`). `companies` are workspace-owned, and `projects.company_id` is nullable with a composite foreign key that prevents a cross-workspace company link (`202609270001_companies.sql:3-27`). The migration associates the internal `weftos` project with WeaveLogic and expressly leaves client company associations to the owner (`202609270001_companies.sql:29-40`). The dashboard code exposes company/project association (`app/page.tsx:152-168`). A search of dashboard migrations and app code for `site` and `fleet` found no site or fleet model at the checked revision. This is a schema and workflow gap, not evidence that the deployed Vercel instance has the same state.

The dashboard's harness credentials may be project-specific or workspace-wide; the read function filters tickets by the credential's project UUID (`202609260008_project_harness_credentials.sql:1-8,38-68`). They are board credentials, not deployment grants. Dashboard project UUID and WeftOS project ULID therefore require an explicit binding, never a name or slug match.

## Proposed entity and authority contract

| Record | Stable key and parent | Meaning / rule to validate |
|---|---|---|
| Company | dashboard UUID + workspace UUID | Customer/organizational account and primary contact; whether this record must be a legal entity is still undecided. One company may own many root nodes and many projects. Display name is mutable; never use it as a cloud resource ID. |
| Root node | new dashboard UUID + company UUID + observed WeftOS identity | Stable operational root independent of company and project names. Bind to a verified node/instance identity; record its governance parent and certification, not an inferred one-root-per-company relation. |
| Project | dashboard UUID + company UUID + workspace UUID | Business delivery scope. WeftOS itself has multiple projects. Keep nullable company only for existing unassigned projects; require a deliberate association before client provisioning. Root association is an explicit binding, not a derived company lookup. Preserve the UUID and history of a predecessor after consolidation. |
| Project succession | predecessor project UUID + successor project UUID + dated decision | Explicit lineage for split, merge or replacement, including many predecessors to one successor. Record who authorized it and why; never rewrite old project IDs or infer succession from similar names. |
| Site | new dashboard UUID + project UUID | An optional physical or logical location. Store typed address/region/time zone and optional geometry with privacy tier; support several sites per project. |
| Fleet | new dashboard UUID + project UUID + certified WeftOS binding | Autonomous governed operational boundary. It carries certified identity and locally effective policy/chain, continues its permitted work if PG/dashboard is disconnected, and reports receipts on reconnection. A fleet may span several sites (as WeaveLogic's does), or have no site binding. Start with one company owner per fleet; decide whether cross-project fleet sharing is allowed before schema work. Associate to root nodes through explicit bindings only. This is a target contract, not a claim that the current fleet runtime is complete. |
| Fleet–site binding (`fleet_sites`) | fleet UUID + site UUID + validity dates | Optional many-to-many association: zero rows is valid; validate the fleet and site share the authorized company/project scope. Do not put one `site_id` on fleet as its entire location model. |
| Root binding | root UUID + project or fleet UUID + verified authority | Deliberate, auditable association to one or more appropriate roots. Do not infer its count from company membership; settle minimum/maximum cardinality in the schema decision. |
| Installation | provider/account/region + immutable external resource ID + fleet UUID | Actual provisioned substrate, with environment (`dev`, `staging`, `prod`), state, and Terraform run reference. A resource may move sites without changing identity. |
| WeftOS binding | fleet UUID + WeftOS project ULID + mesh/instance identity | Explicitly verified link after enrollment; record certificate fingerprint and observed status separately from desired dashboard state. |

These rows are proposed contracts, not existing tables. Enforce same-workspace ancestry with composite keys or equivalent checks and RLS for every new table. Company → many root nodes is the user's 2026-10-04 domain correction; project/fleet → root cardinality remains a schema decision and every association needs an explicit verified binding. Do not equate a dashboard root record with a machine node or ADR-103 primary instance by name alone: ADR-103 gives the primary a governance genesis and permits subordinate instances (`docs/adr/adr-103-weave-topology-roles-and-instances.md:51-53`), while its machine node, user daemon and project kernel have different keys and responsibilities (`ibid.:24-42`). Built WeftOS identity receipts include OS UID → user-key approval (`weaver mesh bind approve <uid>`, `crates/clawft-weave/src/commands/mesh_cmd.rs:399-415`), user-signed project certificates (ADR-103 D7/A7), node proof of possession and `node.registered` (`crates/clawft-weave/src/daemon.rs:4370-4443`), and a Seed-specific signed workload-node bind (`crates/clawft-weave/src/commands/workload_node_cmd.rs:1-27`). None of these establishes a generic dashboard company/root/fleet ownership claim by itself. The user has been asked which existing claim method they mean; the explicit business-to-certified-identity authorization binding remains a design decision pending that answer. Keep desired fleet–site assignments separate from node-observed locations, each with source and observation time; a detected node at a site cannot silently change the desired binding. Make fleet ownership and site assignment explicit so that future “acting for a client” records the client company UUID, requested operation, operator/service principal, and auditable grant. The current PG rollout manages only WeaveLogic-owned fleets. PG and the dashboard submit proposed work and observe receipts; the fleet's certified WeftOS authority evaluates enrollment, Cog and harness placement against effective governance and writes auditable decisions to its own chain. The fleet continues locally under that policy when the dashboard or PG controller is disconnected. This target follows ADR-099's governed placement and audit decision (`docs/adr/adr-099-governed-workload-placement.md:41-54`) and ADR-103's primary/subordinate chain model (`docs/adr/adr-103-weave-topology-roles-and-instances.md:51-67`); the current PG runtime does not yet implement the full contract. Keep dashboard portfolio state separate from the machine/user/project chains that own runtime decisions (ADR-103). On PG, the user requires a separate Linux user and rootless Podman store/runtime for **each project**; bind each project identity to its host UID and container storage without giving it the `weavelogic` operator account's home, credentials or runtime. The `weftos` account satisfies the first account boundary and Podman works rootlessly under that user, but the container storage and persistent user-service lifecycle are not yet governed by Terraform. A fleet can contain several nodes and one primary instance with subordinate instances; development, staging and production are separately governed instances and promotion is a chain-recorded hand-off (`docs/adr/adr-103-weave-topology-roles-and-instances.md:51-63`). Confirm whether those instances share a fleet row or each need a fleet of their own.

Company A is the user's consolidation example: roughly five existing projects are becoming a near-singular v2. The user describes this company as under their own control, so it may be a first-party PG pilot; keep its company, project, root and installation records distinct rather than generalizing that control to customers. Treat the old projects and v2 as separately identified records linked by explicit predecessor/successor edges. Keep the old project, deployment and audit history readable. Review each fleet, root and installation binding against the successor's intended scope, then record a deliberate rebind or retirement with effective time and authority; a succession edge alone moves no running resource or access grant. This is a user-provided scenario, not a verified inventory of Company A's records.

Heartbeat and tailnet presence are discovery hints, never proof of an admitted mesh identity. Show the selected roots, fleet, owner, project, environment and node, with a fleet-wide view and per-node detail. Before later customer access, scope the same query and panel to the caller's company, root bindings, projects, sites and fleets; require a verified ownership claim and a recorded grant for operator actions on behalf of another company. Roles distinguish read from control; an acting-on-behalf-of mutation records both operator and client principal. Add a narrow server-side broker and operation-specific grants before dashboard-triggered mutations; no host token in query strings, browser storage, Terraform state or dashboard database. Gate for the current rollout: WeaveLogic can launch the manager away from PG and sees its authorized OS components across multiple roots and hosts, including disconnected and stale nodes; unbound external fleets do not appear as manageable. Later customer gate: another company's principal sees only its authorized fleet data; a read-only role cannot control it; an unauthenticated heartbeat cannot acquire a trusted badge; revoked grants fail.

Finish the drafted Cog Host tests, formatting, full required gates and remote-appliance bind review before a commit or deployment.
