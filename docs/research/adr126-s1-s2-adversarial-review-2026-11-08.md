## No finding (and why)

- **Bucket derivation across kinds** (`name.rs:99-105`): the `n-`, `p-`, `w-` and `r-` prefixes are fixed, the ULID is a fixed 26 lowercase characters, and node ids are restricted to `[a-z0-9-]` (`name.rs:45`). No two kinds map to one bucket. `weftos-archive` is not derivable from any name, so it cannot be granted (`policy.rs:22`).
- **No grants means deny-all at RustFS**: `put_policy` replaces an empty statement list with `Deny s3:* arn:aws:s3:::*` (`rustfs.rs:374-379`), and `apply_principal` disables the key (`service.rs:318-319`). The live test asserts both (`rustfs_tests.rs:110`).
- **Revoke on the success path**: the backend push completes before `Ok`, and the RPC answers `revoked: true` only after it (`service.rs:353-354`, `store_rpc.rs:114-115`). The governed path refuses at once from the table. The failure and race cases are F2.
- **Non-admin reaching the operator plane**: every `store.*` verb, `store.worktree.*` included, needs Admin (`capability.rs:269`). Literal scopes are refused for supervised children and other uids (`daemon.rs:4060-4074`), and the relay strips them (`relay_auth.rs:43-46`). A project token carries write, never admin (`daemon.rs:4052-4054`). The reach that does exist is F1.
- **Fetch traversal**: `safe_join` refuses `..`, absolute paths and empty segments (`overlay.rs:115-127`). It refuses dangerous segments and every symlinked component, the final one included (`share.rs:614-629`). The SHA-256 is checked before the write (`share_fetch.rs:190-195`). Writes go through a `create_new` temp file and a rename, so a hard-linked target is replaced, never written through (`share_fetch.rs:199-216`). A differing local file is kept without `--force`.
- **Tombstone against object**: the object wins in promotion (`promote.rs:200-204`), and a put clears the tombstone (`overlay.rs:227-229`).
- **Follower writing outside the cache**: the slug is validated before `safe_join(cache, slug)` (`follower.rs:278-281`), and prunes go through `safe_join` (`follower.rs:295-299`). The cache path itself is in F1.
- **Secrets in outputs**: no RPC reply, `svc.store` reply (`store_svc.rs:65-106`), audit event or error string contains a secret or a presigned URL. Errors carry the S3 code and message (`rustfs.rs:170-181`), and request URLs hold no credentials. No presigned URLs are generated.

## Not established

- Whether RustFS 1.0.4 returns 200 with an `<Error>` body on CopyObject (F16), and whether the PG endpoint is loopback or `https` (F15).
- Whether cog calls on `svc.store` can come from another node. `store_svc.rs:56` always builds `Caller::local`, which skips the exposure check (`service.rs:440-444`).
- Whether broker instance ids are unforgeable. `cog:<instance id>` is the whole principal (`store_svc.rs:56`), so a cog that can register under another instance's id inherits its grants.
- Whether owner tokens are issued for off-host use and whether the IPC TCP relay is enabled on PG. This decides whether F1 is a blocker there.
- Canonical-request correctness against RustFS for keys with non-ASCII bytes, `+`, `~` or spaces. Only the ignored live tests exercise this.
- RustFS's behaviour for `Deny arn:aws:s3:::*` on account-level actions (ListAllMyBuckets, admin API) for a principal key. The live test checks bucket operations only.
- Whether a disabled user's existing multipart upload can still be completed. S0 shows only that the next request is refused.
- Whether Admin-capability refusals of `store.*` at the RPC layer are recorded anywhere beyond tracing. They are not in the store's activity log.
- The field names of the audit stream and of notifications. The ADR already lists these as unverified.
