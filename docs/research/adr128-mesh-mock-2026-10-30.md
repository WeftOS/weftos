# ADR-128 mesh mock: a real project over the filesystem mesh

Date: 2026-10-30. Status: run complete, gates M0 to M4 passed. Owner brief, 2026-10-30.

The T0-T5 proofs ran on synthetic trees. This mock runs the ADR-128 flow on a real
project (WeftOS itself) across three real machines. The workflow around it is faked with
scripts; nothing here has to work inside WeftOS yet.

## Roles

| Machine | Role | Holds |
|---|---|---|
| PG | File server and metadata authority only | Project bucket in RustFS, the RVF layer store and lineage, git, the integrator. All merging happens here. |
| The CI host | CI/CD agents. No coding. | Local CoW branches of layers it was handed, a toolchain, build caches. |
| The MacBook | Development | Local CoW branches. It already has a WeftOS checkout, which it adopts rather than re-downloads. |

Run rules (owner):
- Clients never run git. Git exists only on PG, behind the integrator.
- Clients branch locally with CoW and do not know about siblings.
- PG is the only place layers are merged.
- A remote-to-local copy of the whole tree never happens. Clients fetch metadata, then
  fetch blobs lazily, and only blobs they do not already have.

## Pieces

All of this reuses the ADR-128 spike crates in `/Volumes/ai-models/research/`
(tree, compose, publish, integrator).

- **Blob store:** a RustFS bucket for the project on PG, content-addressed (SHAKE-256 of
  the chunk). A dedicated RustFS user scoped to that bucket. Credentials live in 0600 files
  on each machine and are never printed or committed.
- **RustFS is the only data plane.** Clients read and write blobs straight to RustFS S3.
  File bytes never pass through the tree service. Sealed layers are RustFS objects too.
- **Layer store (in RustFS, indexed by PG):** sealed RVF layers (T2 entry format, T4 seal and dual signature),
  plus a lineage record per layer: parent, author machine, role, wave.
- **Tree service (PG):** a small HTTP service on the tailnet, run as the `weftos` user.
  Operations: `get-layer`, `put-layer` (compare-and-swap on the parent head), `list`,
  `integrate`. No ssh tunnels.
- **Client tool:** `meshctl` on the CI host and the Mac.
  - `checkout <layer>` builds a working directory from the composed layers, fetching
    missing blobs from RustFS.
  - `branch` opens a local CoW layer over a layer.
  - `seal` hashes and signs the upper layer.
  - `publish` uploads new blobs, then the layer.
  - `adopt <dir>` indexes an existing checkout and reuses every file whose hash the
    server already has.
- **Integrator (PG):** T5. It turns layers into git trees with `merge-tree --write-tree`
  in lineage order and records conflicts as data.

## Scenarios

Each scenario is a script with gates. At every gate it records wall time, bytes moved,
metadata round trips, disk use and conflicts.

1. **Prepare, develop, test, in waves (owner example).**
   - The CI host branches main, runs the dependency prep (npm install in `docs/src`,
     `cargo fetch`), seals and publishes a prep layer.
   - The Mac branches the prep layer, does a wave of scripted development edits, and
     publishes. The CI host picks the layer up, branches it, and runs scoped checks and
     tests.
   - Meanwhile the Mac branches its own last layer for wave N+1 and keeps working.
   - The Mac's fan-out grows 1 → 2 → 4 → 8 → 16 parallel branches per wave.
   - Post-op: PG merges everything, first flat, then as a tree of merges (pairs, then
     pairs of pairs) at depths 1-4. Compare conflict counts, time and the final tree
     against a plain git merge of the same edits.
2. **Hot files.** Many branches touch the same files (`Cargo.lock`, a shared `mod.rs`, a
   docs index). Measure the conflict rate, whether CoW ordering makes the merge
   deterministic, and what share the integrator resolves without a human.
3. **Main moves underneath.** PG integrates while branches are still out, so branches are
   N layers behind. Measure re-checkout cost, how much read-through it costs, and how many
   blobs refetch versus reuse.
4. **Shared heavy layers.** `node_modules` and `target/` as shared read-only prep layers
   under many branches. Disk and transfer with sharing versus per-branch copies.
5. **Cold joins and adoption.** A fresh tree on the CI host, versus the Mac adopting its
   existing `~/weftos` checkout. Bytes moved, time to first build.
6. **Faults.** Kill a client mid-publish (partial blob set), restart the tree service, and
   flip bytes in a stored layer. Everything must fail closed, and a retry must converge.
7. **Deep chains.** Branch-of-branch to depth 100. This finds where the known ~80-level
   read-through stack overflow and the cost of one-level parent read-through bite.
8. **Publish races.** Two clients publish on the same parent at once. Compare-and-swap
   must let exactly one through, and the other rebases and retries.
9. **Audit.** Every put and integrate is logged with its signer. A rule-breaking client
   (for example a publish without a signature) is cut off.

## Results

Mock crate, scripts and README: `weftos-mesh-mock` on the research volume (outside this repo). Two small tools: `meshd` (PG, metadata service and integrator) and `meshctl` (clients). Clients ran no git. Reports for each run are JSON under the mock's results directory.

### What differed from the plan

- **The registered project root on PG is not empty.** `/data1/weavelogic-internal/weftos` is the live install root (binaries, services, state, releases). It was not touched. The seed clone, the integrator repository and the service state live in a `mesh-mock` directory under the services directory instead, run as the `weftos` user.
- **Blobs are packed.** A bucket write ceiling made one object per file unusable (below). Blobs under 512 KiB are packed into 8 MiB pack objects with a server-side location index; large blobs stay loose.
- **Local copy-on-write is two different things.** The Mac uses an APFS clone. The CI host has no reflinks and no root, so it uses an unprivileged user-namespace overlayfs over a stack of tiny per-layer directories, mounted at one fixed path.
- **Identity and signing:** Ed25519 only (no ML-DSA-65). Request identity is a header, which scenario 9 shows is a weakness.
- **Mac builds:** none. Edits are scripted (add a function plus a test, a `Cargo.toml` edit, a docs edit, a symbol rename, hot-file edits). Scoped `cargo check`/`cargo test` ran on the CI host.

### M1 and M2: scenario 1, prepare, develop, test in waves

Each lane is an APFS clone of a sparse prep working directory (the Mac skips `node_modules` and `.cargo-home`, so those blobs are never fetched). Each wave: four scripted edits, seal, sign, publish. The CI host starts a scoped check on each published layer (a test on the last wave) while the Mac moves on to the next wave. Post-op, PG merges every dev layer in four ways.

| Fan-out x waves | Layers | Mac fan-out (clone cost) | Mac per wave | CI jobs, avg command | CI drain after last wave |
|---|---|---|---|---|---|
| 1 x 2 | 2 | 1.9 s | 0.7 to 1.2 s | 2, 7.9 s | 13.7 s |
| 2 x 3 | 6 | 2.2 s, 6 MB | 1.1 to 1.3 s | 6, 14.6 s | 30.8 s |
| 4 x 3 | 12 | 3.2 s, 12 MB | 2.0 to 2.3 s | 12, 15.5 s | 42.6 s |
| 8 x 3 | 24 | 6.0 s, 25 MB | 4.6 to 5.0 s | 24, 31.9 s | 122 s |
| 16 x 2 | 32 | 11.2 s, 53 MB | 17 s, 31 s | 32, 58.5 s (max 274 s) | 388 s |

Fan-out 16 is feasible. The Mac side grows with contention (16 processes scanning 5.9k files each); the CI host's 16 cores are the limit at 8 parallel `cargo` jobs. The rest of the CI time is compute, not the layer machinery: a job's setup (mount, lower stack) is under a second.

Post-op merge on PG, same layers every time. Flat is the canonical `(depth, name)` order with `git merge-tree --write-tree`. Tree-of-merges groups layers by arity (pairs, pairs of pairs, ...) and merges groups; on a group conflict it falls back to merging that group's members one at a time.

| Layers | Variant | Levels | Merge ops | Merge time | Merged / conflicts | Final tree vs flat |
|---|---|---|---|---|---|---|
| 6 | flat | 1 | 5 | 227 ms | 6 / 0 | n/a |
| 6 | tree, arity 2 and 3 | 3, 2 | 5 | 204, 189 ms | 6 / 0 | same |
| 6 | plain `git merge` | | | 3,576 ms | 6 / 0 | same |
| 12 | flat | 1 | 11 | 428 ms | 11 / 1 | n/a |
| 12 | tree, arity 4, 3, 2 | 2, 3, 4 | 11, 11, 13 | 603, 453, 642 ms | 11 / 1 | same (1 fallback at arity 2) |
| 12 | plain `git merge` | | | 5,447 ms | 11 / 1 | same |
| 24 | flat | 1 | 20 | 651 ms | 16 / 5, 3 blocked | n/a |
| 24 | tree, arity 5, 3 | 2, 3 | 27, 32 | 1,399, 1,685 ms | 16 / 5 to 6 | same |
| 24 | plain `git merge` | | | 8,181 ms | 16 / 8 | same |
| 32 | flat | 1 | 30 | 1,386 ms | 20 / 11, 1 blocked | n/a |
| 32 | tree, arity 6 | 2 | 48 | 2,189 ms | 20 / 11 | same |
| 32 | tree, arity 4, 3 | 3, 4 | 53, 53 | 3,217, 3,072 ms | 19 / 12 | **different** |
| 32 | plain `git merge` | | | 7,839 ms | 20 / 12 | same |

- **Flat equals plain git.** The flat tree hash matched a plain `git merge` of the same layers at every size. The flat merge is 6 to 17 times faster, because it never checks out a working tree.
- **Natural conflicts rise with fan-out** (0 of 6, 1 of 12, 5 of 24, 11 of 32). Most are docs files that two lanes both appended to (a docs pool of about 100 files and 32 edits); some are crate files. A conflicting layer is recorded as data and skipped, and a stacked layer on top of it is reported blocked.
- **One-time git import:** each layer costs 0.3 to 0.8 s to become a git commit on PG (a blob fetch and a plumbing `hash-object` per file). Merge cost per layer is then 40 to 100 ms.

**Merge-depth finding.** A deeper merge tree buys nothing here, and it costs correctness when there are conflicts:

1. Merge operations grow with depth (30 flat, 48 at 2 levels, 53 at 3 or 4 levels for 32 layers), because every group conflict triggers a member-by-member fallback. Time followed (1.4 s, 2.2 s, 3.1 to 3.2 s).
2. With no conflicts, or few, every depth gives the same final tree as flat. With 11 conflicts, arities 4 and 3 landed a different set (19 merged against 20) because the conflict was decided between groups instead of in `(depth, name)` order. Only the flat order matches git.
3. The depth that would pay is where independent groups merge in parallel (a critical path of levels times the per-merge time instead of the sum). The mock merges serially in one process, so that gain is not measured. For 32 layers at arity 4 it would be about 3 levels of 3 merges, an estimate of roughly 9 merge times against 30.

**Scenario 2, hot files.** N branches each edit the same three shared files (`Cargo.lock`, a shared `lib.rs`, a docs file) plus their own crate.

| N | Style | Landed automatically | Conflicts | Flat merge | Plain git | Same tree under shuffled and reversed arrival | Plain git reversed gives the same tree |
|---|---|---|---|---|---|---|---|
| 4 | same spot | 1 of 4 | 3 | 217 ms | 3,643 ms | yes | no |
| 8 | same spot | 1 of 8 | 7 | 499 ms | 4,305 ms | yes | no |
| 16 | same spot | 1 of 16 | 15 | 921 ms | 6,245 ms | yes | no |

| 8 | different spots | 8 of 8 | 0 | 657 ms | 3,631 ms | yes | yes |
| 16 | different spots | 16 of 16 | 0 | 1,565 ms | 5,334 ms | yes | yes |

Tree-of-merges at arity 2 and 4 gave the same tree as flat in all six runs. The winner of a same-spot collision is the layer with the lowest name at its depth, which is deterministic but arbitrary. The integrator resolves line-level edits to distinct places in the same file without a human (all 28 of 28 here) and never resolves two edits at the same place (the loser is data: path, hunks, git's messages). Semantic conflicts (a merged result that does not compile) were not run; the CI host runs on single layers only.

**Scenario 3, main moves underneath.** PG integrates a group of branches and exports the result as a new main layer (1.1 to 1.6 s, 14 to 22 ops). The branches still out catch up with `rebase`: main's changes since their common base are applied, their own changes are kept and re-sealed on top.

| Integrated first / still out | PG integrate | Export | Caught up cleanly | Blobs fetched, bytes (clean catch-ups) | Rebase time | Re-publish | Needed PG (same path changed on both sides) |
|---|---|---|---|---|---|---|---|
| 4 / 4 | 221 ms, 0 conflicts | 1.5 s | 1 | 1 blob, 301 KB (a changed `Cargo.lock`) | 1.7 s | 0.7 s | 3 |
| 8 / 4 | 584 ms, 1 conflict | 1.6 s | 1 | 1 blob, 301 KB | 1.8 s | 0.8 s | 3 |
| 4 / 8 | 252 ms, 0 conflicts | 1.1 s | 2 | 0 blobs | 0.9 s | 1.5 to 2.2 s | 6 |

A fresh checkout of the new main into a warm cache is 2.1 to 3.6 s and moves 0 bytes (a cold cache is scenario 5). The metadata round trip for a new layer is one small fetch (its ops over the cached parent tree), not a full tree. **Limit:** the client rebase is path-level, so any file changed on both sides is sent to PG, even if the edits are far apart (5 of 8 late branches here, by design of the edits). The integrator does merge those.

**Scenario 4, shared heavy layers** (2.4 GB, 87,136 files, on the CI host; eight parallel jobs):

| Case | Result |
|---|---|
| Full hard-link checkout of the layer (read-only farm) | 0.8 s, 87k links |
| Per-branch full copy | 5.2 s and 2,387 MB each |
| Overlay branch over the shared layers | under 1 s to mount, 0.24 MB of upper per cold-check job |
| Eight cold checks of one crate in parallel (target outside the tree) | 14.3 s total, 13.6 s average (CPU-bound) |
| Warm target layer (`target/`, built once) | 400 files, 64 MB, published as one pack in 11 s |
| Eight checks on the warm layer in parallel | 12.8 s total, 57 MB of upper each (files copied up) |
| One check on the warm layer, alone | 5.5 s, 15 to 19 compile units rebuilt, against 8.5 s cold |
| Cold CI client fetching the warm layer | 67.9 s, 2,288 MB, 77,372 blobs, 6,526 requests; first build 5.7 s, 19 units rebuilt |

Sharing works for disk and branch cost (a branch is megabytes, not gigabytes). It did not make the build state shareable: a `target/` restored from layers is not treated as fresh by `cargo`, even at the same absolute path. Layers carry no file mtimes, and cargo's fingerprints compare mtimes (and bake in absolute paths). The same path fix (one fixed mount path for every job, private to each job's mount namespace) is needed but was not enough alone. A target layer needs mtimes in the entry attributes (kept out of the layer name), or the build outputs need hashing on a fixed clock.

### M4: scenarios 6 to 9

**Scenario 6, faults.** All failed closed and a retry converged.

| Fault | Observed |
|---|---|
| Client killed with SIGKILL 5 s into a 780 MB publish | the layer was not visible on the server (no partial layer). Retry: 85 s, re-uploaded everything (811 MB, 3,024 blobs), because none of the 24 in-flight loose uploads had finished. Then visible; a fresh client checkout verified clean |
| meshd restarted mid-publish | the client was in its blob upload (it does not talk to meshd then); the layer landed after restart. Restart takes about 10 s (it re-verifies every stored layer's name and signature, and the base against git). The retry reused all 24 blobs |
| meshd restarted while a client polls once every 0.5 s | 4 of 19 polls failed, over 1.7 s; the client has no retry of its own |
| A byte flipped in a stored layer file on PG | at restart meshd renamed it to `.quarantined`, logged it, and refused to serve it (and would drop any layer stacked on it). Re-publishing the layer from the client restored it |
| A byte flipped in a stored blob | a fresh client refused it: `blob ... fails its hash`. After the object was repaired, checkout succeeded |
| Tree after a restart | identical hash before and after (layers 464 to 465 with the new one) |

The mock's server only checks that a blob exists when it accepts a layer; it cannot catch a rotted blob until a reader hashes it. A scrub is a B2 item. A killed publish leaves orphaned pack objects with no registry entry; they need garbage collection.

**Scenario 7, deep chains** (a lane chain of 100 layers, each a child of the last):

| Measure | Result |
|---|---|
| Commit cost by depth | flat: 1.6 s at depth 1, 1.2 to 1.3 s at depth 25, 50, 75, 100 (average 1.28 s) |
| Server diff (prep layer to depth d) | 0.6 s (d=1), 1.0 s (10), 2.6 s (50), 2.1 s (100) |
| Cold checkout of the depth-100 head | 20 s, one full tree fetch, 99 MB |
| PG integrates the whole chain | 105 s: 79 s one-time git import (0.8 s per layer), 25 s for 99 merges |

The mock flattens a chain on the server, so read-through depth never reaches a client; the cost of depth is on PG (tree reconstruction) and in the one-time git import.

**Scenario 8, publish races.** Eight Mac clients and one CI-host job publish at the same moment against one ref head (compare-and-swap).

- Exactly one publish won the first round (the CI host's racer lost with a 409 and did not retry).
- The losers rebased onto the new head and retried: all 8 landed in 16.5 s, 36 attempts in total (the winner count per round is one, so the cost is quadratic: the last client needed 8 tries).
- The ref's history is one straight chain of 8 layers that reaches the prep layer. All 8 clients' edits are in the final tree (checked by hash).

**Scenario 9, audit.**

- Every put, integrate, export, register, block and unblock is in an append-only log with the signer: machine, action, layer, result, detail.
- A client that published with its signature removed got a 403 and was cut off. Its next, validly signed publish was refused ("machine is cut off"); so was a replay of another machine's signed layer under its name. The Mac and the CI host kept publishing. An operator unblock restored it.
- **Weakness:** the machine name comes from a request header. A well-formed request naming another machine with a bad signature cut that machine off; the CI host's next publish was refused until an unblock. Requests need to be authenticated (signed, or by a client certificate) before a strike counts.
- Layer names are deterministic (same edits, same time, same name), so a repeated run stores nothing new.

### Follow-ups after M2

**The small-write cap: observed, cause not proven to be RustFS.** The cap is flat across 8 to 128 writers (24, 43 and 42 objects per second from the Mac). Run from PG against the same S3 endpoint it is the same: 38 per second at 32 writers and 14 per second at 4 writers (about 26 ms per request, serialised). So it is not the WAN. RustFS here has `RUSTFS_AUDIT_ENABLE=true` with a webhook sink on loopback. The sink is a single-threaded Python `HTTPServer` that opens and appends to a file per event; 100 serial POSTs to it took 1.56 s (about 64 per second including curl start-up), the same order as the cap. A synchronous per-request audit POST would produce exactly a flat cap like this. I did not read RustFS's own per-request timing, and I did not change its configuration (Terraform-managed). To confirm: repeat the burst with audit off in a throwaway instance, or time the sink. Until then, read "43 per second" as a property of this configured instance, not a RustFS limit. Packing is still the right design (it also cuts requests 10 to 20 times for a tree of small files).

**What is in RustFS, and what is not.** Bucket `proj-weftos` at the end of the run: 9,633 loose blob objects (3.36 GB; this includes the two 780 MB fault-test payloads and benchmark objects) and 521 pack objects (1.10 GB). **Layers now live in RustFS** (moved after M2; the first runs kept them on PG's local disk): 583 sealed layers as `layers/<name>.json` objects (21.1 MB), a lineage record beside each (`lineage/`, 0.14 MB), and 523 pack indexes (`packidx/`, 13.3 MB). The objects are JSON, not RVF files: the mock's layer is a signed delta, not an RVF lineage. meshd keeps only refs, keys, per-layer status, the audit log and an in-memory copy; its local state is now about 56 MB of which the old layer files are an unused leftover. The 584 existing layers were migrated by meshd at start (it uploads any local layer file the bucket lacks) and all resolve, including the wave-1 parent layer and the base (verified against git HEAD again). Restart quarantine still works from S3: a byte flipped in one layer object was caught at the next start (name and signature check), the object moved to `quarantine/`, the layer returned 404 and its count dropped by one. File bytes never went through meshd or ssh: clients and the integrator read and wrote blobs directly against the bucket. S3 requests summed from the clients' own counters (a lower bound: some one-off runs did not write metrics): the Mac 348 requests, 2.0 GB up, 0.6 MB down; the CI host 928 requests, 2.3 GB up, 3.2 MB down (its cold-join runs are not in these); the PG seeding client 5,878 requests, 99 MB up. Metadata round trips to meshd: Mac about 990, CI host 928. meshd's own requests (existence checks on publish, blob fetches for git import) are not counted.

**What the integrator does with a conflict (this matters).** A conflicting layer is excluded **whole**, not path by path. `git merge-tree` reports a conflict for the layer as a unit; the integrator leaves the merged head unchanged, records the layer, its conflicted paths and the conflict hunks in the response, and carries on. A layer stacked on an excluded layer is reported blocked. So one conflicting file removes all of that author's other, clean changes from the merged head too. Counts from the runs:

| Run | Layers | Excluded whole (conflict) | Blocked | Paths in conflict |
|---|---|---|---|---|
| Fan-out 4 | 12 | 1 | 0 | 1 |
| Fan-out 8 | 24 | 5 | 3 | 5 |
| Fan-out 16 | 32 | 11 | 1 | 11 (one file each) |
| Hot files, same spot, N=4, 8, 16 | 4, 8, 16 | 3, 7, 15 | 0 | 3 files each layer (lock, shared source, docs) |

Tree-of-merges at arity 3 and 4 (fan-out 16) excluded 12 layers against flat's 11: the extra layer was merged by flat and excluded by the tree. Flat's choice follows `(depth, name)` order, so it is reproducible; the tree's depends on grouping.

**Finding against an ADR-128 requirement.** The scripted runs excluded whole layers silently (11 of 32 at fan-out 16) and those layers lost their clean edits too; ADR-128 §7 promises that conflicts are recorded as data and nothing is lost quietly. This is fixed in the wave tooling by durable conflict records (per-layer status in meshd, a conflict record file with both sides, and a generated fix-up task), but the scripted-run numbers above were produced without it.

**Is the author told? Not in the scripted runs.** The result goes back to whoever called `integrate` and one line goes into the audit log (merged and conflict counts, not layer names). Nothing is persisted per layer, and an author has no call to ask "was my layer excluded". That is a gap, not a pass. Excluded work is not lost (the layer, its blobs and its lineage stay stored and signed), but it is silent to the author. The wave tooling needs a durable conflict record per excluded layer (files, both sides' hunks, parent) and a fix-up task generated from it; hot-file branches 2 to N are the case that exercises it (N-1 whole layers, each with an otherwise clean crate edit).

### Wave tooling (real tasks)

Scripts in the mock crate: `prepare-wave`, `publish-wave`, `ci-wave`, `integrate-wave`, `review-queue`, and `run-layer-job.sh` (check out a layer and run a command: one call, container-ready). Self-test on one task: edit, publish (1.2 s, 22 KB), acceptance on the CI host (67 s for `cargo check -p clawft-weave`), flat merge (0.8 s), export of the new head, and a git-format review patch. Conflicting or CI-failing layers are written as durable records plus a ready fix-up task file whose parent is the new merged head; the server keeps a per-layer status (`merged` or `excluded-conflict` with files and hunks) that survives restarts. Review patches are only written, never applied.

**What real tasks showed that scripted edits did not:**
1. **Conflicts are rare and clustered.** Scripted fan-out 16 gave 11 conflicts in 32 layers; real tasks, with deliberate overlap groups, gave 1 in 41. The one that happened was two agents appending a test module at the same file end.
2. **The checks themselves are the weak part.** 4 of 5 rework items were not bad code: a filter that skipped a test (T27), two acceptance commands naming crates outside the workspace (T22, T36), and a test-count gap that exit 0 hid. Only T39 was a defect in the agent's work. The acceptance command has to be validated as part of the task (it runs, it matches the tests it should, the package exists).
3. **CI, not the layer machinery, sets the pace.** Branch dirs prepare in 2 to 22 s, publishes take about 1.8 s each, the merge is seconds; CI drain is minutes and depends on one slow crate.
4. **A no-op is a valid result.** T27-fix1 made no edit and its unfiltered run over the head passed; the tooling needed a path for "verify, do not publish".
5. **Agents work as a small, safe diff.** 36 patches range from +0/-3 to +72/-1 lines, one or two files each.

**Open findings for ADR-128 (nothing here is closed by the mock):**
- **mtime:** layers carry no file mtimes, so a restored `target/` rebuilds. The entry must carry mtime (outside the layer name) or derive it deterministically.
- **Signed identity:** the mock identifies a request by a header. The real path is per-node signed requests; a spoofed header cut another machine off.
- **Cold join:** slower than a public clone plus install (90 s against 32 s on the CI host). The win is adopt and warm joins.
- **Write cap:** observed (about 43 small writes a second, also from PG itself); the audit sink at about 64 requests a second serially is the likely cause. Unproven; nothing was changed.
- **Harness spawn limit:** 17 simultaneous agent launches failed 7 on lock contention; batches of about 4 worked.
- **Test-filter gap:** exit 0 does not prove tests ran. `ci-wave` now sums passed tests across all binaries and checks that added test names ran; it also needs a check that the acceptance package exists.
- **Layers and merges:** conflicts exclude a whole layer; the durable record and fix-up task are what keep that from being silent.

### What this changes in ADR-128

1. **B2, publication:** layers must publish packs of small blobs (8 MiB) with a location index, not one object per chunk. The bucket's small-write ceiling (about 43 per second) is the limit that decided it. Add a scrub for rotted blobs and garbage collection for orphaned packs. Metadata should be binary and compressed (a prep layer's JSON was 12.9 MB).
2. **B3, mount route:** local copy-on-write on a host with no reflinks and no root is a stack of per-layer directories under an unprivileged overlay, mounted at one fixed path in a private mount namespace. A hard-link farm per layer does not scale (ext4 caps links at 65,000 per inode, which broke it after a hundred-odd derived working directories). Whiteouts for removals are plain character devices any user can create.
3. **Entry attributes (an ADR change):** the entry must carry the file mtime, kept out of the layer name so names stay deterministic, or mtimes must be derived deterministically on materialise (for example from the layer's logical time, with outputs ordered after inputs). Without one of these a `target/` restored from layers is not fresh, and ADR-127 §3 (caches as layers) does not work.
4. **§7, merging:** keep the flat `(depth, name)` merge as the canonical one. It matched plain git at every size, it is independent of arrival order, and it is 6 to 17 times faster than git merge in a working tree. A merge tree is only worth it with parallel groups, and then it needs a rule that makes the conflict decision order-independent.
5. **§7 and B4, rebase:** a client rebase can only move disjoint paths; any file changed on both sides goes to the integrator. Say so, or give clients a request-a-merge call.
6. **B2, security (a requirement, not a pass):** a request header as identity is a mock shortcut. The real path is per-node signed requests (each request signed with the node's key, checked against the registry) before any strike counts. Scenario 9 shows what happens without it.
7. **Cold joins:** a cold join from the layer store is slower than a public clone plus install here (CI host 90 s against 32 s; Mac 19 s against 9 s). The win is adopt (nothing moves) and warm joins (a few seconds, no bytes). Fetch lazily by path (the mock's sparse `skip` worked: the Mac never fetched 2 GB of dependencies) and treat the layer store as the way to adopt and to branch, not as a faster public install.
8. **Conflicts are whole-layer and silent:** record every excluded layer durably with its paths and hunks, tell the author, and generate a fix-up task; do not rely on a response body.
9. **Layers in RustFS:** sealed layers are objects in the bucket; meshd keeps only refs, compare-and-swap, status and a cache (done in the mock after M2; start-up now lists and verifies every layer over S3, which adds to restart time).
10. **Server load:** meshd's restart takes about 10 s because it re-verifies every layer and the base; the stored layers need an index or a checkpoint at scale.
