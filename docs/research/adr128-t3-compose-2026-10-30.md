# ADR-128 T3: compose one view from five independent layers

Date: 2026-10-30. Verdict: **T3 passes** on all four bars, on the WeftOS compose walk. U3 (multi-parent RVF, upstream issue #1289) is not needed for this to work; if it lands it changes only where the walk lives.

Crate: `weftos-compose-spike` (sibling of the T2 `weftos-tree-spike` and T5 `weftos-integrator-spike` crates, path deps on both, `Layer`/`Frozen`/`ComposedView`). Layers are independent lineages, listed top to bottom: job tip (writable), then sealed layers. Each sealed layer carries tree records, key/value facts and vector memories. A sealed layer from T5 enters through `Layer::from_sealed_full` (a base) or `from_sealed_delta` (the change against its parent, with tombstones for removals). Layers made directly are named by a SHAKE-256 content hash.

## Precedence table

| Record type | Rule |
|---|---|
| Tree entry | The highest layer with a record for the path decides. A tombstone is a record: it hides every lower entry for that path. |
| Tree, under a hider | A tombstone or a non-directory entry at a proper ancestor in layer L hides every lower layer's entries beneath that ancestor. L's own records beneath it still count. A directory entry hides nothing. |
| Directory listing | Union of child names over all layers; a name is kept only if `lookup` of the child path finds an entry. So the tree rules above apply to listings. `readdir` of a path that is absent or tombstoned is `NotFound`; of a non-directory, `NotDir`. `/` always exists. |
| Key/value fact | The highest layer holding the key decides. A `None` value is a tombstone and hides lower values. |
| Vector memory | Union by id. If an id appears in several layers the highest layer's vector is the one used. Results order by squared L2 distance, then equal distance by layer (top first), then id. Vectors of the wrong dimension are skipped. |
| `diff(tip)` | The tip's records compared with the view below it: a put that differs from (or is absent below) the lower view, and a tombstone for a path that exists below. No-ops are dropped. Sorted by path. |

Layers are expected to be self-contained: lookup does not check that a record's parent directory exists in the same layer. `promote_tip_into(target)` is implemented as a plain copy of tip records, facts and vectors into a writable layer (no conflict check; the T5 integrator owns real promotion).

The view name is SHAKE-256 over a domain tag, the layer count, each sealed layer name in order, and the tip's base hash. Reordering layers or changing the tip base changes the name (tested).

## Numbers against the bar

Release build, Linux kernel listing: 97,313 files, 103,658 entries in the base. Four more layers of 100, 300, 800 and 2,000 records (about 20 percent tombstones, some new paths).

| Bar | Result |
|---|---|
| Compose 5 layers under 100 ms | First call 1.5 us, median 0.5 us, p99 0.7 us, max 9.2 us over 2,000 runs. Compose clones five `Arc`s and hashes 5 names. |
| Cost to make the base layer (not part of compose) | Index build 84 ms, content name 45 ms, once per layer, then shared by `Arc`. |
| Lookups through 5 layers vs 1 | 691 ns/op (1.45 M/s) vs 201 ns/op (4.98 M/s) on random base paths: 3.4x. Base-only paths, which miss four layers first: 707 ns/op. |
| `readdir` 5 layers vs 1 | `/` (42 entries) 21 us vs 6 us; `/drivers` (146) 75 us vs 24 us; `/drivers/net` (64) 34 us vs 9 us. About 3x. |
| `diff` of a tip with 201 writes | 50 us. |

Lookup cost grows with the layer count, as expected, and stays under a microsecond. The extra cost over one layer is the per-layer hash probes plus the ancestor probes when a layer holds hiders.

## Determinism hashes

A `probe` binary builds a seeded five-layer stack and prints the view name. Three fresh processes in three different working directories:

- Synthetic stack (5,000 paths): `77ece7c1a5700591001ff9da47d70f7398973fe26e0d4d40d7963c5fceaaaac6` in all three. A fourth run in `/` matched.
- Linux listing stack (97,313 files): `d306bfc2938aa1883b1955010ea1f75e48416d0bd9776685e67690031f1610ee` in all three.
- The bench stack (different seed use) names itself `8e3eb46feef0da11b13e90f34ad6d6ad9df457b0408f94442a855bf114371ccb`.

The automated test `tests/determinism.rs` spawns the probe in three temp directories and asserts equality. Nothing path-, time- or ordinal-dependent enters a layer name. This stands in for two nodes; the two-node run waits on Tailscale.

## Property-test coverage

`tests/model.rs`: 3,000 random cases per run, 1 to 5 layers of 0 to 11 random operations over paths from a 3-letter alphabet to depth 3 (39 paths plus `/`), plus a random tip. Operations are put file, put directory, tombstone, key/value set or tombstone, vector add. The reference model flattens the layers bottom up with a different algorithm (a hider deletes lower entries by prefix first, then the layer's records apply) and is compared on every path for:

- `lookup`, including tombstones and re-created directories under a lower tombstone;
- `readdir` (the exact sorted listing, `NotFound` and `NotDir` cases);
- `diff` against the model's below-the-tip flatten;
- `kv_get` on every key;
- vector `search` (union, id shadowing, tie order).

Also: a hand-built three-layer tombstone/re-create case, a promote round trip, and `tests/sealed.rs`, which builds real T2 trees, seals them with T5, and composes a sealed delta, an independent role-pack lineage, a base and a fact layer.

## What is not shown

- Two nodes: one machine, three processes.
- Layers are held in memory. Loading them from RVF files is T2's path; the 84 ms index build is what reading a 100k-entry layer costs once, assuming the flatten is no slower than the build here.
- Vector search is brute force; one tiny layer only shows the union rule.
- Unsealed (tip) state is not persisted by this crate.
